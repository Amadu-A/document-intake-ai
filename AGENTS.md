# Document Intake AI — обязательные правила для Codex и других AI coding agents

## 0. Назначение и приоритет

Репозиторий: `Amadu-A/document-intake-ai`. Разрабатываем **законченный, пригодный к развёртыванию** FastAPI-монолит для автоматической обработки входящей/исходящей корреспонденции и других документов. Первый законченный бизнес-сценарий — письма «под ключ». Не подменять рабочую интеграцию демонстрационным UI, stub/mock или MVP.

Порядок приоритетов: явные решения владельца → фактический код и зафиксированные контракты этого репозитория → актуальный `main` `Amadu-A/shared_infrasktructure/docs` → defaults библиотек. При конфликте обозначить его; не менять утверждённые решения молча.

Перед **каждым** изменением:

1. Проверить локальные `git status`, ветку, HEAD, diff и актуальное состояние доступного remote. Изучить полные тексты затрагиваемых файлов, контрактов, тестов и конфигурации.
2. Прочитать актуальные `docs/LLM_CONTEXT.md` и необходимые по задаче `docs/ENGINEERING_GUIDELINES.md`, `docs/FRONTEND_GUIDELINES.md`, `docs/INFRASTRUCTURE_INSTRUCTIONS.md`, `docs/services.yaml` из `Amadu-A/shared_infrasktructure`. Для web читать Frontend Guidelines **полностью**; для shared — Infrastructure Instructions и services.yaml.
3. Сверить фактический runtime с реестром: реестр описывает назначение, **не** доказывает состояние контейнеров. Не применять изменения к общему стеку без отдельной команды владельца.
4. Не выполнять `git commit`, `git push`, `git reset --hard`, force push и изменение чужих ресурсов без прямой команды владельца. Не использовать `git add .`.

## 1. Утверждённые функциональные инварианты

- Вход: **один или несколько файлов**, включая PDF, DOC, DOCX, TXT, JPG, PNG, TIFF, низкокачественные сканы, многолистовые изображения и объединённые пачки из нескольких документов. Приводить страницы к общей последовательности, сохранять оригиналы, исходный порядок и происхождение каждой страницы. При наличии нескольких исходных файлов сохранять связку `(source_file_id, physical_page_number)`.
- **Именно shared-VLM принимает все семантические решения о границах самостоятельных регистрационных документов и принадлежности приложений**. Docling извлекает OCR/layout/таблицы, backend выполняет техническую нормализацию и проверяет целостность, но **не заменяет решение VLM собственным эвристическим splitter'ом**. Заголовок «Акт», дата, печать или смена контрагента сами по себе не дают backend права разрезать файл.
- Сначала VLM составляет план группировки страниц с обоснованием и принадлежностью приложений, затем backend проверяет корректность плана (страницы существуют, не потеряны, не повторены, ссылки разрешимы). При нарушении — автоматический ограниченный повторный запрос VLM с описанием ошибок. Backend не исправляет семантические границы самостоятельно. Если корректный план получить нельзя, вернуть **структурированный статус ошибки / неполного распознавания и ссылку на исходный файл**; не выдумывать границы, не скрывать страницы и не объявлять результат успешным.
- **В автоматическом режиме (`auto_split=true`, `skip_segmentation=false`) никаких обязательных вопросов и подтверждений.** Legacy API без новых полей сохраняет этот режим. В режиме предложения VLM (`false/false`) извлечение начинается после подтверждения; в режиме `false/true` исходные файлы задают группы, а ручные изменения требуют подтверждения. Сочетание `true/true` запрещено. Низкая уверенность фиксируется честно.
- `4-2591.pdf` — регрессионный пример: **один регистрационный документ** из страниц 1–6, основная претензия на страницах 1–2 и четыре приложения (акты на 3, 4, 5, расчёт пени на 6). Не регистрировать эти приложения как отдельные письма. При этом два независимых письма в одном скане должны стать двумя регистрационными документами.
- Вторая стадия shared-VLM: строгое определение рода/вида/подвида и извлечение реквизитов. Для писем классифицировать **строго по утверждённому закрытому справочнику**, без придуманных типов; для неписем пока возвращать доступный род, предварительный вид, извлечённые реквизиты, файл и warnings, **не** пытаться подгонять их под письма.
- Роды документов: `Внутренние документы компании`; `Входящая/Исходящая корреспонденция`; `Договоры`; `Документы связанные с исполнением договоров`; `Процессуальные документы`; `Составляющие документы договора`. В пределах переписки направление (`incoming`/`outgoing`) определять относительно обслуживаемой организации, а не по слову «Исх.» на бланке отправителя. Если организация не установлена — `null` и warning, не подменять факт догадкой. Не требовать от пользователя обязательного уточнения.
- Переписка: использовать пути вида `Входящая/Исходящая корреспонденция → Входящее письмо / Исходящее письмо → вид → подвид (если есть)`. Зафиксировать полный утверждённый справочник в версионированных данных репозитория и покрыть проверкой принадлежности каждому enum/пути. Динамическая генерация новых видов VLM запрещена.
- Извлекать максимально доступные **поисковые реквизиты**: входящий/исходящий номер и дату документа, отправителя и адресата, организации и идентификаторы (ИНН, КПП, ОГРН), контакты, тему, номера/даты договоров, спецификаций, счетов, заказов, актов, связанных писем, суммы, сроки, подписантов, приложения, краткое содержание. Не выдумывать отсутствующие поля; для неоднозначностей использовать `null`/warning. Внутренние регистрационные номера и статусы 1С не выводить из исходного PDF.
- **Не создавать `one_c_matching`, `candidates`, `duplicate_status`** или другой служебный объект поиска кандидатов в 1С. Сервис только распознаёт документы; программист 1С самостоятельно делает поиск, сопоставление, регистрацию и прикрепление из полученных реквизитов. Полный OCR-текст в публичный JSON не включать.
- Сохранять **первоначально утверждённую JSON-структуру `schema_version: "1.0"`**: `batch_id`, `files[]`, `files[].documents[]` и вложенные `classification`, `requisites` (включая `attachments`, `related_entities`), `one_c`, `attachment_file`, `recognition`, `warnings`. Не переименовывать и не ломать поля без отдельного согласования. Промпты версионируются независимо от схемы. `documents[]` содержит регистрационные единицы, `requisites.attachments[]` — их приложения. Для многодокументного файла вернуть несколько элементов `documents[]`, для претензии с актами — один.
- Каждой регистрационной единице соответствует отдельный **готовый PDF-комплект**, включающий основную часть и все относящиеся к ней приложения. Возвращать доступный для 1С `http://<server-ip>:<port>/api/...` download URL с ограниченным временем жизни; не выдавать `storage://`, локальный путь или `#page` вместо фактического скачивания. Сохранять ссылку и на исходный файл. 1С может скачать PDF и прикрепить его без участия web UI. Вычислять размер и SHA-256 для проверки целостности; не подставлять фиктивные значения.
- Оригиналы, разделённые PDF, JSON, рендеры, OCR-промежуточные данные и временные файлы живут **1 час после завершения** задания (успех, ошибка или отмена). Ожидание ручного решения/запуска — максимум 1 час после готовности всех превью; подготовка имеет отдельный конечный deadline. После TTL API немедленно отказывает в доступе; физическая очистка идемпотентна, не затрагивает активные задания. Скачанный 1С файл не зависит от TTL нашего сервиса.

## 2. Два промпта и Web UI

- Два независимых **редактируемых** промпта: (1) семантическая группировка/разделение регистрационных документов и приложений, (2) классификация + извлечение реквизитов. Использовать утверждённые версии как основу; не менять смысл без согласования.
- Модальное окно «Промпты» содержит **две вкладки** сверху. Отдельные тексты, сохранение на текущую анонимную сессию, восстановление базового текста активной вкладки. Запущенное задание использует неизменяемые snapshots обоих промптов.
- Светлый инженерный UI: горизонтальная виртуализированная лента страниц и диапазонов над тремя колонками; слева просмотр, в центре состав документов, справа JSON/реквизиты/этапы. Автоматический режим не требует подтверждения. В остальных режимах разрешены ручные split/merge/move/create/exclude/undo/reset и подтверждение, без изменения исходных файлов.
- FastAPI + Jinja2 + обычный CSS/JS: semantic HTML, BEM, разделённые CSS/JS модули, один CSS entrypoint, data-attributes для JS, без inline `onclick`, без инъекции недоверенного HTML. Web и внешние клиенты используют одни и те же application use-cases и REST API; бизнес-логика не дублируется в шаблонах/роутерах.

## 3. Архитектура, API и обработка

### Режимы и разметка — утверждено 09.11.2026

- `POST /uploads` сразу ставит подготовку превью в собственную очередь, без OCR/VLM. Неполный пакет нельзя подтвердить. Ожидание пользователя ограничено одним часом после готовности превью; очередь, подготовка и анализ имеют отдельные конечные deadlines.
- Первая ручная правка атомарно меняет режим на `auto_split=false`, `skip_segmentation=true`, источник `manual`/`manual_override` и увеличивает ревизию. Сохраняются исходное VLM-предложение, draft, неизменяемый approved snapshot и минимальный аудит. Optimistic revision, owner и fencing проверяются сервером.
- Автоматические семантические границы по-прежнему определяет только VLM. Ручной план и технические границы исходных файлов не передаются в строгий VLM-validator как будто они проверены моделью. После подтверждения VLM извлекает факты внутри фиксированных групп и не меняет их страницы.
- Страница может быть явно исключена пользователем: остаётся в исходнике, manifest и preview, но не входит в регистрационный PDF. Каждая физическая страница ровно один раз назначена либо явно исключена. Автоматическая VLM-разметка сохраняет полное покрытие без исключений.
- `awaiting_confirmation` освобождает worker и lease. После lock/extraction редактирование запрещено; повторный confirm одной ревизии идемпотентен. Старые поколения не публикуют план/результат после правки.
- До 400 МиБ/1000 страниц на источник и регистрационную группу; пределы источника, комплекта и пачки настраиваются независимо. Нагрузочная готовность подтверждается замерами, а не только значениями Settings. Shared Docling/VLM не перенастраиваются ради лимитов.
- Новые рендеры `document_intake_mode_*` и интерактивный HTML используются только как локальные reference и не публикуются без отдельного разрешения владельца.

### Уточнение владельца 11.11.2026 — большие и перемешанные пачки

- Связанные листы могут быть разделены 1–5 чужими страницами. Несмежные PageRef одной
  регистрации допустимы; объединение решает VLM либо явно пользователь.
- При ошибках VLM после ограниченных повторов, неподтверждённых auto-границах или
  исчерпании бюджета разделения разрешён технический черновик по одному листу:
  `page_fallback`, `awaiting_confirmation`, обязательные проверка/confirm.
  Это исключение из прежнего auto без подтверждения, прямо разрешённое владельцем.
  Нельзя объявлять такой черновик успешным распознаванием или выдавать финальный JSON.
- Разделение выполняется VLM по рендерам; OCR всей пачки не является предусловием
  проверки границ. Docling используется после фиксации состава для реквизитов.
- Историческое уточнение 11.11.2026 предлагало 1–4, 5–6, 7, 8. Оно заменено
  решением владельца от 12.11.2026 ниже; письмо и повестка по-прежнему не объединяются.

### Уточнение владельца 12.11.2026 — корреспонденция и проекция 1С

- Для `суд_ув.pdf` подтверждены четыре комплекта: **[1,8], [2,3,4], [5,6], [7]**.
  Конверт и повестка связаны совпадающим номером дела и сторонами; близость к
  постановлению пристава не является доказательством. Приватный полный эталон —
  `examples/суд_ув.expected.json`, диапазоны — `examples/суд_ув_cut.json`.
- Направление независимо от юридического рода: неписьмо может быть incoming/outgoing
  при доверенном контексте организации и подтверждённых сторонах, с template_path=[].
  Без контекста direction=null с warning; получатель PDF не становится нашей организацией.
- Поля one_c формирует backend после проверки VLM-фактов: доверенная организация,
  внешний отправитель, каталог письма, явный факт письменного ответа и краткое содержание.
  Папки, адресат 1С, форма, способ получения и проект без утверждённого контекста — null.
  VLM возвращает one_c с null; публичная структура JSON 1.0 сохраняется.
- Обязательства явки/удержания не означают письменного ответа. Номера дел/производств
  и даты заседаний/состояния расчётов не подменяют собственные номер/дату документа.
- В этой доработке не менять инфраструктуру, Compose, env, секреты и TTL.

- **Один проектный FastAPI-монолит**, собственные API и worker-процессы, PostgreSQL для состояния/сессий/событий, Jinja2 web. Слои `domain` → `application` (use-cases + маленькие ports) ← `infrastructure`; `presentation/http` и `web` — delivery. Dependency Injection в едином composition root; никакого SQL, RabbitMQ или VLM-клиента внутри route handler.
- Независимые headless endpoints для 1С / Telegram / других клиентов: загрузка одного или нескольких файлов (`multipart`), запуск задания, `GET` статуса, `GET` финального JSON, `GET` скачиваемых PDF и исходников, отмена, SSE-события и snapshot для повторного подключения UI. Для больших пакетов использовать `202 + job_id` и polling; не удерживать запрос на весь VLM-анализ. `GET` result отдаёт только завершённую проверенную структуру или явно маркированную неполноту/ошибку; raw streaming не выдавать за подтверждённые реквизиты. Идемпотентность submit, устойчивость к retry, restart и дублирующим сообщениям обязательны.
- Существующий Docling Serve — только как внешний OCR/layout/table adapter; существующий `shared-vlm` — только как внешний VLM adapter. Отправлять изображения для vision-задач, не полагаться исключительно на OCR. Разбивать большие файлы на окна с перекрытием и сохранять глобальные physical-page identifiers; итоговый глобальный план границ снова решает VLM. Docling может иметь лимит 50 страниц за запрос — **не** делать этот лимит пределом сервиса.
- Никаких внешних облачных AI API. Shared model/GPU/topology не хардкодить: использовать logical endpoint `http://shared-vlm:8000/v1`, model alias `shared-vlm` и сеть `ai-shared`; реальное значение сверять с `services.yaml` и runtime.
- RabbitMQ shared используется только для обмена заданиями; долгоживущие задачи, состояние, SSE-журнал и результаты — в собственной PostgreSQL/хранилище. Ограничить worker concurrency, retries, queue depth, VLM timeout; учесть at-least-once delivery, fencing/lease и очистку. Не создавать свой broker/vLLM/Docling/Redis/n8n без явного согласования.
- Никакой выдуманной нормативной, договорной или бухгалтерской информации. В тестах проверять не только поля, но и границы, вложения, отсутствие потерянных страниц и корректные download links.

## 4. Публикация по IP сервера и безопасность

- Под **«опубликовать наружу»** владелец подразумевает доступ с других машин LAN по IP сервера, **как** `http://192.168.55.3:8083/`, а не обязательное публичное доменное имя, reverse proxy или Internet-facing deployment.
- На данном сервере `8083` занят `spec-extracting-ai`; предложенный для нового проекта начальный порт **`8084`**, после проверки его свободы. Конфиг: `APP_BIND=0.0.0.0`, `APP_PORT=8084`, `APP_PUBLIC_BASE_URL=http://192.168.55.3:8084` в `.env.example` как редактируемые **несекретные** значения. Наружу публиковать только web/API порт своего сервиса. При конфликте порта падать с понятной диагностикой, не менять порт молча.
- Для LAN HTTP допускается `COOKIE_SECURE=false`; при последующем публичном Internet-доступе необходимы HTTPS, `COOKIE_SECURE=true` и отдельное согласование инфраструктуры. Не ослаблять безопасность ради отсутствия экрана входа.
- **Без логина/пароля в web UI**, но анонимные изолированные сессии со случайным HttpOnly/SameSite cookie, CSRF + Origin для изменяющих cookie-запросов, и **раздельные секретные API-ключи интеграций** (1С и Telegram). Не выдавать файл/JSON чужой сессии или интеграционному owner. Download URLs — короткоживущие/подписанные, с проверкой TTL, токены не писать в access-логи. Ограничить upload size/pages/files, rate limits, MIME/signature, PDF/изображения и обработку zip/архивов при расширении.
- Не публиковать PostgreSQL, RabbitMQ, Docling или shared-VLM дополнительно; ограничить доступ к endpoint проекта разрешённой LAN/VPN сетью на уровне firewall при развёртывании. Ни входящие документы, ни их OCR, ни prompts, ни секреты не писать в обычные логи или Git.

## 5. Конфигурация: `.env.example` + `.env`

- Единый Pydantic Settings. **Приоритет:** `.env.example` (полный каталог, defaults, placeholders) → `.env` (только настоящие секреты/необходимые приватные overrides) → environment процесса (наивысший приоритет). Реализовать и протестировать этот порядок для локального Python и Docker Compose. Не применять слепое `source .env` в shell: значение API_KEYS/пароли могут содержать спецсимволы.
- `.env.example` коммитится, `.env` никогда не коммитится. В `.env` не копировать весь `.env.example`; хранить только project-specific секреты (`DATABASE_PASSWORD`, `RABBITMQ_PASSWORD`, `API_KEYS`, session/download signing secret при необходимости). Не читать и не печатать секреты/`.env` соседних проектов.
- **Чтобы после clone работала одна команда**, `scripts/up.sh` обязан на первом запуске **безопасно** создать отсутствующий `.env` с криптографически случайными project-specific секретами (mode `0600`, atomically, без вывода значений) либо обнаружить уже созданный и **никогда не перезаписывать реальные секреты**. Если секреты пользователя требуют внешней авторизации/согласования или уже существует конфликтующая учётная запись — завершиться с инструкцией, а не менять чужие credentials.
- Для Docker использовать совместимую с Pydantic конфигурацию через `docker compose --env-file .env.example --env-file .env ...`, с созданием `.env` до вызова. `docker compose config --quiet`, а не выводить полную конфигурацию с паролями.

## 6. RabbitMQ — строго ограниченный idempotent bootstrap

- Общий RabbitMQ **уже существует** (`shared-rabbitmq-1` в `ai-shared`); **никогда не создавать новый RabbitMQ и не выполнять reset shared stack**. Приложение имеет выделенные `RABBITMQ_USER=document_intake`, `RABBITMQ_VHOST=document-intake` и очередь `document-intake.jobs` (несекретные defaults, изменить можно через Settings).
- Владелец разрешает `scripts/up.sh` создать **только** выделенного пользователя приложения и его vhost в существующем контейнере. До изменения проверять наличие и доступность сервиса; операции только по точному имени собственного user/vhost. Существующие чужие users/vhosts/permissions/exchanges/queues **не трогать**.
- Если пользователь отсутствует — создать с секретом из `.env`. Если уже существует — проверить пароль **без изменения**. При несовпадении **остановиться с ошибкой**: запрещены `change_password`, массовый импорт definitions, удаление/пересоздание учётной записи или изменение чужих прав. Если user имеет права в чужом vhost — остановиться и потребовать выделенную отдельную учётную запись. Создавать vhost только если отсутствует; назначить и проверить permissions только внутри собственного vhost. Повторный `up.sh` не должен изменять существующие secrets или чужие namespace.
- **Не передавать секрет в аргументах CLI, логах, `set -x`, `docker compose config`**; использовать безопасную передачу через закрытый stdin/pipe или другой проверенный способ (с учётом возможной видимости процесса). После bootstrap обязательный real AMQP connect и наличие работающего consumer собственной очереди.
- В приложенном историческом PDRD `scripts/up.sh` присутствует опасное поведение `change_password` при несовпадении пароля существующего RabbitMQ-пользователя. **Не копировать это поведение.** Ориентироваться на безопасную проверку в актуальном `spec-extracting-ai/scripts/up.sh`, сверяя код на момент разработки.

## 7. `scripts/up.sh`: одна команда clone → готовый сервис

В новом репозитории реализовать **действительно идемпотентный** `scripts/up.sh`, запускаемый пользователем как `bash scripts/up.sh` (не просто написать документацию о нём):

1. Проверить наличие Docker/Compose, доступ к daemon, свободный `APP_PORT`, существующую сеть `ai-shared`, reachable shared RabbitMQ, Docling и VLM. Не запускать/перезапускать shared services и не менять их compose.
2. Создать/проверить **только собственные** secrets и sparse `.env`, не изменяя существующие пароли; валидировать Settings и конфигурацию Compose; создать private project directories/permissions без root-owned пользовательских файлов.
3. Ограниченно и идемпотентно подготовить выделенные RabbitMQ user/vhost/permissions и проверить их (п. 6).
4. Собрать собственные Docker images (`api`, `worker`), создать **собственную** PostgreSQL, применить миграции, поднять собственные контейнеры, выполнить recreate собственных API/worker после изменения кода/настроек; не удалять volumes с данными. Использовать уникальный `COMPOSE_PROJECT_NAME`, не запускать `docker compose down -v`, `system prune`, не использовать `--remove-orphans` для чужих проектов.
5. Проверить actual `health/live`, `health/ready`, соединение с PostgreSQL, рабочую очередь/consumer, доступность shared-VLM (vision + JSON contract), Docling OCR, выдачу web, API и внешние download URLs. При отсутствии зависимостей не заявлять READY: дать точную диагностическую причину.
6. Напечатать **только** безопасные адреса UI и `/docs`, например `http://192.168.55.3:8084/`, состояние контейнеров и подсказки для проверки. Никогда не печатать tokens, пароли или целиком `.env`.

`bash scripts/up.sh` должен работать повторно после `git pull` и пересоздавать **только свои** изменившиеся компоненты. Не добавлять отдельные entrypoint-скрипты без объективной необходимости. Явно документировать внешние prerequisites: установленный Docker и уже работающие shared services; если они недоступны, честно остановиться, а не обещать невозможный автономный запуск.
