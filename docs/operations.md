(анализ), worker_attempts_exhausted (восстановления). UI до claim показывает
«Ожидает начала обработки», без вымышленного прогресса OCR.
Readiness принимает живую PG-lease при занятом worker без подписки, но никогда
не маскирует недоступность самого брокера.

Новые defaults: завершённые данные 86400 с, ожидание утверждения 86400 с,
сессия 259200 с с продлением активности. Срок обработки, HTTP и очередь не увеличены.
Настройки не действуют задним числом на уже рассчитанный TTL старых заданий.
Cookie обновляется с тем же owner; очистка cookie теряет анонимную историю. Закрытая
вкладка worker не останавливает. Подписанные download URLs ограничены пятью минутами;
обновите snapshot/result для новой ссылки в пределах срока хранения задания.
Полный интеграционный сценарий и примеры: [API без браузера](integration-workflow.md).

Prerequisites: Linux с Docker daemon/Compose v2, coreutils `timeout`, `flock`, `ss`;
в существующей `ai-shared` работают RabbitMQ, Docling и shared-VLM.
VLM: `http://shared-vlm:8000/v1`, alias `shared-vlm`, без API key.
Текущий shared runtime по умолчанию выполняет длительный reasoning перед JSON.
Приложение явно передаёт `chat_template_kwargs.enable_thinking` из Settings:
`VLM_ENABLE_THINKING=false` по умолчанию запрашивает прямой ответ.
При включении `true` подбирайте `VLM_TIMEOUT_SECONDS` и `VLM_MAX_TOKENS` по замерам
полного ответа с учётом общего `JOB_TIMEOUT_SECONDS`; лимиты автоматически не повышаются.
Docling: `http://docling-eval:5001`, разрешённый `DOCLING_API_KEY` обязателен.
Ключ предоставляет владелец общей инфраструктуры; проект не читает чужие `.env`.
Для проверенного Docling Serve 1.38.2 каталог задаёт `DOCLING_OCR_PRESET=tesseract`
и `DOCLING_OCR_LANGUAGES=["iso:ru","iso:en"]`. При необходимости меняйте список
языков JSON-массивом доступных runtime идентификаторов; `ru`/`en` не эквивалентны
этим идентификаторам языков. Несекретные defaults остаются в `.env.example`.
Хост должен разрешать приложению syscall seccomp и иметь доступ к закреплённым images/PyPI.

Readiness подтверждает зависимости и прохождение технического pipeline;
она не доказывает точность каждого извлечённого реквизита.

Для auto/review Docling OCR предшествует текстовому сравнению соседей.
`PAIR_CONCURRENCY=4` ограничивает одновременные пары одного worker-процесса,
`PAIR_MAX_ATTEMPTS=3` — сохраняемый бюджет каждой пары.
`VLM_SEGMENTATION_TIMEOUT_SECONDS=900` ограничивает этап сравнений отдельно от OCR.
При ошибках остаются неизвестные переходы, `segmentation_source=vlm_partial`,
`awaiting_confirmation`; извлечение ждёт явного утверждения состава.
Успешные пары и OCR переживают restart; изображения не используются для границ.
`DOCLING_MAX_ATTEMPTS=5`, `DOCLING_RETRY_MAX_SECONDS=60`,
`DOCLING_REQUEST_INTERVAL_SECONDS=1` ограничивают повторы/частоту;
429 учитывает Retry-After, реальные secrets менять не требуется.
`DOCLING_ASYNC=true` использует проверенные async/poll/result endpoints существующего
Docling. `DOCLING_TASK_TIMEOUT_SECONDS=600` — отдельный бюджет ожидания конвертации,
`DOCLING_POLL_INTERVAL_SECONDS=5` — пауза polling. HTTP timeout остаётся 180 с.
Task ID хранится только в private checkpoint; restart продолжает ту же задачу.
Старый sync-контракт доступен только явным `DOCLING_ASYNC=false`; он не устраняет
продемонстрированный timeout тяжёлого 20-страничного OCR-окна. Если task/result
исчезли у shared Docling, сервис диагностирует отказ, не ставит слепо дубликат.

`DOCLING_WINDOW_CONCURRENCY=2` ограничивает все одновременно обрабатываемые OCR-окна
одного адаптера процесса, включая несколько документов. Размер окна остаётся 20 страниц;
после byte-деления дочерние части выполняются в том же слоте. Завершения могут прийти
в любом порядке: прогресс растёт по готовым окнам, конечная последовательность сохраняет
исходные `(file_id, page_number)`. Для последовательного режима передайте несекретный
`DOCLING_WINDOW_CONCURRENCY=1` через environment или каталог `.env.example`.
Пересоздайте собственные API/worker обычным `bash scripts/up.sh`; shared Docling не меняется.
Общий POST lock удерживает только интервал отправки; polling и ожидание выполнения
идут без него. Retry-After задаёт общий cooldown следующих POST, уже принятые задачи
продолжают ожидаться по прежним ID. Отмена/ошибка отменяет и дожидается остальных
корутин; начатая запись checkpoint завершается до возврата отмены.

`WORKER_CONCURRENCY=3` ограничивает число основных заданий процесса.
Два OCR-окна ускоряют одну большую пачку. Самостоятельные задания используют только
заданное число worker slots. Реплики API/worker имеют отдельные лимиты;
прочие потребители shared Docling также могут занять его очередь.

Worker пишет безопасное JSON-событие `ocr_task_timing`: `task_ref` — хеш ID,
`wait_ms` — текущее ожидание с чтением результата, `observed_queue_wait_ms` — интервал
до первого наблюдаемого started, `observed_execution_ms` — от него до наблюдаемого
завершения. `timing_source=client_poll`: это приближение с задержкой polling/сети,
не серверные timestamps. Если started не наблюдался, отдельные интервалы `null`.
При `resumed=true` очередь неизвестна, время выполнения охватывает только текущий
сеанс ожидания. Ошибка/отмена отражается в `status`, payload и исходный task ID не пишутся.

Для отдельного реального замера с примерами на 173, 6 и 8 страниц, после настройки
разрешённого `DOCLING_API_KEY` в `.env`:

```bash
DOCLING_BASE_URL=http://127.0.0.1:5001 bash scripts/test.sh --live -s tests/test_live_docling_concurrency.py
```

Команда рассчитана на Docker-host с loopback-портом Docling. Внутри `ai-shared`
используйте штатный Docker DNS. Тест не меняет исходные PDF, shared-конфигурацию и
credentials; сравнивает новые отдельные кеши при лимитах 1/2, число task, page coverage,
порядок, повторное чтение кеша и пересечение реальных started. Частная матрица с
временами и OCR-хешами сохраняется в `reports/local/ocr-concurrency-live.json`.
Прогон вызывает настоящий OCR дважды для большого файла и может занять десятки минут.

UI/API используют отдельные `READ_RATE_LIMIT_PER_MINUTE=600` и
`PREVIEW_RATE_LIMIT_PER_MINUTE=2400`, управляющий лимит остаётся 120/min.
Не увеличивайте их для обхода ошибки: сначала проверьте code отказа.

Базовые версии промптов: разделение v5, извлечение v6. Для существующей сессии:
«Промпты» → нужная вкладка → восстановить базовый текст → сохранить.
Неизменённые сохранённые старые базы обновляются автоматически. Пользовательские
тексты и snapshots уже запущенных заданий сохраняются. Для проверки исправления
классификации загрузите прежний неудачный пакет заново; terminal job не перезапускается.

Каждый готовый блок сначала классифицируется, затем извлекаются общие реквизиты
и профильные детали D01–D11. Неизвестная категория получает kind_code=null и warning.
Судебные проверки собственных и связанных дат действуют также для неписем.
`classification_failed`/`extraction_failed`
сохраняют остальные результаты пакета; причины видны в `document_processing` API и UI.
Потребитель 1С должен проверять статус блока перед регистрацией. PDF доступен и для
блока с диагностируемой ошибкой. Неполный пакет завершается `completed_with_warnings`.
`VLM_WINDOW_PAGES` ограничен восемью страницами; продолжения помечаются явно,
итоговые реквизиты согласуются из проверенных частей. Полный пакет в один запрос
извлечения не передаётся. Готовый блок имеет приватный durable checkpoint и не требует
повторной VLM при restart; OCR использует прежний кеш. Общий deadline остаётся конечным.
Новых секретов, миграций и изменений shared-сервисов для этой доработки нет.
Штатный HTTP smoke требует `recognized` для своего тестового письма. Доступные JSON/PDF
с заглушкой или неподтверждёнными реквизитами не дают ему объявить PASS.

```bash
bash scripts/up.sh
```

Скрипт проверяет daemon/Compose/сеть, собирает один образ API/worker и атомарно создаёт
отсутствующий sparse `.env` случайными независимыми секретами.
Можно заранее записать в `.env` только разрешённый `DOCLING_API_KEY`.
Существующие непустые секреты сохраняются; отсутствующие или пустые добавляются.
Невалидные заданные секреты не заменяются: скрипт останавливается с безопасной диагностикой.
Собственный обычный файл получает права `0600` без изменения содержимого;
symlink, hardlink, устройства и файлы другого владельца отвергаются.
Системная блокировка исключает одновременный bootstrap. Существующий `.env` дополняется
одной записью `O_APPEND` и `fsync`, без replace/truncate; до и после проверяются
содержимое и inode. Это не атомарный compare-and-swap с внешним редактором.
Редактировать `.env` во время `up.sh` нельзя. Обнаруженный конфликт останавливает
запуск до настройки сервисов; пользовательские байты сохраняются без rollback.
При конфликте проверьте файл и удалите лишние дубликаты самостоятельно: повторные
непустые значения секретов bootstrap отвергает. Для обычного редактирования
дождитесь завершения `up.sh` и повторите запуск.
Первый запуск без внешнего Docling key намеренно останавливается до RabbitMQ bootstrap;
добавьте только выданный ключ в созданный `.env` и повторите команду.
Права чужого файла автоматически не меняются.

Далее проверяет `APP_PORT`, существующий RabbitMQ-контейнер и его принадлежность `ai-shared`.
Разрешены только создание выделенного user/vhost и permissions своего vhost.
Существующий пароль проверяется без изменения; неверный пароль, служебные теги или
права user в чужом vhost останавливают процесс. Password передаётся закрытым stdin
в приватный RAM-файл, не через argv. `set -x` отключён до работы с секретами.
После bootstrap идут реальные OCR и vision/JSON пробы, своя PostgreSQL и миграции,
запуск/recreate своих API/worker, real AMQP/consumer и readiness.
Образ запускает единственный Tini как PID 1; дополнительный init в Compose не нужен.
Для неожиданных ошибок operations выводит тип и координаты кадров без текста
исключения, исходных строк, аргументов и значений локальных переменных.
Затем synthetic HTTP smoke по внешнему адресу проверяет web/API, настоящий pipeline,
JSON и скачивание с checksum клиентом без cookie/API key. Это собственный тестовый
документ, автоматически удаляемый по обычному TTL.

При повторе после `git pull` образ пересобирается, Compose пересоздаёт изменившиеся
собственные компоненты. Shared stack, чужие namespaces и volumes не удаляются.
Изменения `.env` процесса влияют на все команды с тем же приоритетом, что Pydantic.
При изменении настроек очереди уже существующая очередь может отклонить несовместимые
arguments; скрипт не удаляет её и не заменяет молча. Согласуйте миграцию очереди отдельно.

Обновление с сохранением видимых логов:


Offline tests требуют `uv` и Python 3.12–3.14. `up.sh` не требует uv/Python хоста:
использует собственный образ. `--live` требует поднятый сервис, evaluation key в
собственном Settings и локальные `examples` (пять прежних пар и две новые пары
диапазонов). Если что-то отсутствует, это FAIL,
а не успешный skip. Частные сравнения/замеры сохраняются в игнорируемый `reports/local/`.

Отдельная проверка доставки:
`bash scripts/test.sh --live -s tests/test_delivery_live.py tests/test_ack_timeout_live.py`.
Нужен доступ к локальному Docker и заранее загруженные образы `rabbitmq:4.1-management`,
`postgres:16.15-alpine`, `document-intake-ai:local` (образ обычного `up.sh`).
Другой готовый образ окружения указывается флагом `--delivery-image=имя:тег`.
Стенд создаёт только
собственные временные контейнеры/сеть с префиксом `document-intake-delivery-`,
loopback-портами и случайными secrets; shared стек и `.env` не использует.
Исходный код приложения монтируется из текущего checkout; в worker подменена только
длительная бизнес-операция. Это проверка реальной доставки/PG/AMQP, а не качества AI.
Сценарии: backlog более 30 с, потеря настоящего AMQP confirm, разрыв соединения,
SIGKILL worker и restart PG/RabbitMQ/worker с сохранёнными volumes.
Дополнительно: изолированный consumer_timeout=60000 мс, работа дольше 130 с,
одна активная/три ожидающих, аварии до claim/до ACK/после ACK,
обрыв соединения между commit и ACK, продолжение checkpoint.
Проверка занимает несколько минут; shared consumer_timeout не изменяется.

Browser prerequisites: доступ к download Playwright и системные библиотеки Chromium.
Скрипт автоматически ставит закреплённый Chromium при флаге browser.
Запуск: `bash scripts/test.sh --browser`, Windows —
`.\ops\check-quality.ps1 -Browser`. Browser-тесты используют настоящие HTTP/Chromium,
но synthetic OCR/VLM; это не подтверждение качества реальной модели.
Тест 501 страницы отдельно проверяет раннее первое превью, затем ждёт кнопку запуска
до 120 с. Это запас функционального E2E, а не изменение серверных deadline или SLA
скорости подготовки. Замеры сохраняются в `tmp/browser-501-preparation.json`.
Обе команды полной проверки отключают необязательный pytest cacheprovider: недоступный
старый `.pytest_cache` не вызывает предупреждений, его файлы и права не меняются.
Если Execution Policy блокирует локальный `.ps1`, используйте разовую команду
`powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1 -Browser`.
Она не меняет постоянные политики Windows.

Ручная приёмка из другой разрешённой LAN/VPN-машины:

Перенос листов доступен после готовности всех превью и до подтверждения диапазонов.
Выберите лист (Ctrl/Cmd — несколько), используйте «Лист назад/вперёд» либо
«Переместить…». В диалоге задайте позицию текущей ленты и «перед/после»;
подсказка показывает источник, исходный номер и диапазон назначения. Переносимые
листы войдут в этот диапазон. Undo отменяет последнюю правку этой вкладки,
reset восстанавливает первоначальный состав и порядок. После ACK/reload порядок
сохранён на сервере и попадёт в PDF-комплект. Исходные номера всегда видны рядом.

Тот же перенос доступен мышью: захватите миниатюру, наведите на левую/правую половину
целевой и отпустите у маркера вставки. Для нескольких листов сначала выделите их
Ctrl/Cmd или Shift. У края лента прокручивается автоматически. Escape или отпускание
за пределами ленты отменяет перенос. Ручки ↔ по-прежнему редактируют только границы.

«Разрезать и скачать» рядом с подтверждением фиксирует сохранённый состав и ждёт
классификации/извлечения, затем скачивает один `documents.zip`. Внутри — PDF всех
утверждённых блоков в выбранном порядке: папки `doc_1`, `doc_2` и далее,
в каждой — `Полное название № номер от ДД.ММ.ГГГГ.pdf` без префикса номера блока.
Имена отдельных скачиваний совпадают с basename ZIP; дубликаты имеют (2), (3).
Слеши официального номера отображаются как `／`, номер в JSON сохраняется исходным.
При неизвестных реквизитах соответствующих частей имени нет. Приложения входят
в комплект, исключённые листы остаются в исходнике. Reload сохраняет намерение
скачать текущий пакет. После готовности архив можно скачать повторно; ошибка
сборки показана рядом с кнопкой и допускает повтор без новой VLM-обработки.
«Новый пакет» отменяет отложенное скачивание. Архивы имеют тот же TTL, что и PDF.

В большом просмотрщике кнопки ↶/↷ поворачивают страницу на 90°; 100% вписывает
повёрнутую ширину, увеличение даёт прокрутку. Угол сохраняется для каждой страницы
в текущей вкладке, в том числе после reload и завершения обработки. «Новый пакет»
очищает углы. Это настройка просмотра: OCR, оригинал и скачанный PDF не поворачиваются.
Для перестановки уже заблокированного задания создайте новый пакет.

1. Открыть `http://192.168.55.3:8084/` без экрана входа; `/docs` загружает локальный Swagger.
2. Проверить две вкладки промптов, отдельные тексты, восстановление только активной,
   сохранение сессии и сохранность другой вкладки после обновления страницы.
3. Загрузить `4-2591.pdf`, запустить анализ. Ожидать 1 регистрацию, страницы 1–6,
   четыре приложения и warning о расхождении дат. Подтверждать границы не требуется.
4. Проверить листание, миниатюры, масштаб; обновление SSE не меняет выбранную страницу.
5. JSON до завершения помечен как поток. После проверки — schema_version 1.0,
   экспорт доступен, PDF-комплект содержит 6 страниц, исходник скачивается отдельно.
   Сверить род, номер и дату самого письма с оригиналом: номера/даты договора
   и приложений не должны подменять эти поля. Фактические результаты и ограничения
   приведены в текущем отчёте проверок.
6. Пачка с двумя независимыми письмами даёт две регистрации/PDF. Несколько источников
   сохраняют file_id/page_number в manifest; TIFF сохраняет порядок кадров.
7. Ошибка/отмена показывают диагностический статус и исходники; экспорт неподтверждённого
   JSON недоступен. После TTL ранее выданные ссылки запрещены.
8. Повторить `up.sh`: текущие credentials сохраняются, чужие RabbitMQ users/vhosts не меняются.

Приёмка редактора после обновления:

1. Auto: явно выбрать «Разделить автоматически» (`true/false`); загрузка показывает прогрессивные превью ещё до анализа,
   Start заканчивается JSON без подтверждения.
2. Review: выбран по умолчанию, карточка «Предложить разделение для проверки». После предложения VLM увидеть
   `awaiting_confirmation`, выключенный экспорт, кнопку подтверждения. После confirm — PDF/JSON.
3. Skip: выбрать «Без автоматического разделения» (`false/true`). Два отдельных файла дают
   два PDF без segmentation-VLM и без обязательного confirm.
4. Manual-first: сразу после превью разделить диапазон, перетащить границу, повторить
   стрелками/Enter/Escape. Проверить сохранение и выбор режима без автоматического разделения.
   Попробовать Merge, Undo, Reset, исключение страницы и Create для её восстановления.
5. В двух вкладках отправить правку одной revision: вторая получает 409 и актуальный план.
   После подтверждения кнопки редактирования заблокированы; refresh сохраняет состав.
6. Исключённая страница остаётся в оригинале/preview, отсутствует в PDF-комплекте.
   Проверить ручные две группы `4-2591.pdf`: ровно два PDF по выбранным страницам.
7. Пакет на 200/1000 страниц: выбирать файл, переходить по сквозному номеру, прокручивать
   ленту. В Network — page API порциями, в DOM — до 24 карточек, viewer сохраняет выбор
   при SSE/polling. Большой pipeline измерять отдельно от скорости UI.
8. На 501 странице листать и прокручивать ленту: нет сообщения rate_limit, выбранный
   лист сохраняется, повторные polling не скачивают одни миниатюры десятки раз.
9. Для перемешанных листов выбрать первый, Ctrl/Cmd-кликнуть связанный несмежный,
   нажать «Создать диапазон»: чужие листы между ними остаются в своих группах.
   Разделить несмежный диапазон, обновить страницу, проверить порядок и сохранение.
10. При неопределённых переходах увидеть предупреждение, прогресс сравнений и метки «?». До
    confirm экспорт недоступен. Проверить состав, подтвердить, скачать PDF и оригинал.
11. «Новый пакет» доступен при загрузке, в очереди, во время OCR/сравнений/извлечения,
    при ожидании и после результата. Подтвердить отмену; экран, выбор, JSON, журнал и
    превью очищаются без перезагрузки. Повторить загрузку того же файла и drag/drop
    после отказа. Ctrl+F5 после сброса не должен восстанавливать старый job_id.
12. Cancel немедленно показывает «Отмена…», затем «Отменено». Поздний ответ старого
    пакета не меняет новый экран. При отказе cancel доступны повтор и явное отсоединение
    с предупреждением, что сервер мог продолжить прежнюю обработку.

Ресурсные параметры в `.env.example`: `UPLOAD_MAX_FILE_MB=400`,
`UPLOAD_MAX_FILE_PAGES=1000`, `DOCUMENT_MAX_MB=400`, `DOCUMENT_MAX_PAGES=1000`,
`UPLOAD_MAX_MB=1024`, `UPLOAD_MAX_PAGES=2000`, `UPLOAD_MAX_FILES=20`.
Файл и комплект ограничены независимо от пачки. Значения MiB, не десятичные MB.
Queue — 14400 с, preview — 3600 с, processing — 14400 с по умолчанию;
waiting — до 86400 с после готовности состава (для одной подготовки — preview_ready),
terminal retention — 86400 с.
`STORAGE_MIN_FREE_MB=1024` оставляет резерв. Реальное место включает оригиналы,
нормализованный PDF, PNG, OCR и комплекты; входные 400 МиБ не равны расходу диска.
Настройки не являются гарантией скорости реальной VLM. Миграция `0002` сохраняет готовые
результаты, но активные задания старого алгоритма завершает с `algorithm_version_changed`:
загрузите их заново. `up.sh` перед миграцией останавливает только собственные API/worker,
затем пересоздаёт их. Смешанные worker разных версий одновременно не запускать.
Неизменённые старые базы обновляются до segmentation-v5/extraction-v6;
пользовательские overrides и snapshots сохраняются.

`/health/ready` не доказывает firewall-доступ из другой машины. Firewall ограничивает
только собственный web/API порт разрешённой LAN/VPN; private PostgreSQL не публикуется.
При будущем Internet-доступе отдельно согласуются HTTPS и `COOKIE_SECURE=true`.
Откат: вернуть согласованную версию кода владельцем и повторить `up.sh`, сохранив `.env`
и named volumes. Автоматический destructive downgrade БД не выполняется.
