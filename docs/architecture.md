# Архитектура и решения

Один FastAPI-монолит, отдельные API/worker-процессы из одного образа.
PostgreSQL принадлежит проекту и находится только в private Docker network.
Внешние RabbitMQ, Docling и shared-VLM подключаются через существующую `ai-shared`.
Физические модели, GPU, topology и lifecycle shared-сервисов проект не настраивает.

`domain` содержит строгие Pydantic-модели экспорта и VLM-плана, каталог шаблонов,
предметные ошибки и правила целостности. `application` использует порты и координирует
сценарии. `infrastructure` реализует PostgreSQL, AMQP, HTTP, конвертацию и файлы.
Composition root — `app/core/container.py`; HTTP handlers не создают драйверы и не содержат SQL.
Jinja2/JS обращаются к тем же сценариям через REST.

Конвейер: загрузка → отдельная progressive preparation → выбранный режим границ →
блокировка состава → PDF → OCR/vision-извлечение → проверка схемы/каталога → публикация.
Auto/review определяют границы по PNG без предварительного OCR всей пачки.
Docling вызывается после фиксации состава; review и резервный черновик не требуют OCR.
Конвертация работает отдельным процессом с timeout. На Linux задаются CPU/address-space/
file-size limits, seccomp запрещает IPv4/IPv6, дочернему процессу не передаются secrets.
Office запускается headless с закрытыми macros и обновлением внешних ссылок;
активные OOXML-вложения и внешние связи отклоняются. Контейнер nonroot/read-only,
capabilities сняты, временная файловая система ограничена.

Docling получает окна до 50 страниц; большие по byte_size окна дополнительно делятся.
VLM получает PNG каждой страницы; окна имеют перекрытие. OCR дополняет vision при извлечении.
Если окон несколько, **сама VLM** принимает окончательный план из предложений окон.
Для больших пачек согласование идёт деревом соседних планов: все группы пересечения
и соседство минимум шести физических позиций снова решает VLM. Это позволяет
сопоставить продолжения через 1–5 чужих листов; состав по-прежнему назначает модель.
Остальные группы сохраняют прежнее решение VLM.
Физические интервалы CompactPlan экономят место; запрос явно задаёт allowed_spans,
обоснование ограничено 500 символами. Backend разворачивает интервалы и проверяет
полноту на каждом уровне, не исправляет семантические границы. Стыки получают bounded
vision-контекст. Малые пачки сохраняют прежний global reconciliation.
Backend проверяет адреса, полноту, уникальность, порядок и отношения основной части/приложений.
Семантических splitter rules, regex по заголовкам и объединения по контрагенту нет.
В auto неподтверждённый план, ошибки покрытия/JSON после повторов или отдельный бюджет
`VLM_SEGMENTATION_TIMEOUT_SECONDS=900` приводят к `page_fallback`: каждая страница
предлагается отдельным черновиком, `awaiting_confirmation`, без PDF/JSON/extraction.
Это явно разрешённый владельцем резервный путь от 11.11.2026, а не решение backend
о регистрационных границах. В review корректный по покрытию план с needs_review
остаётся предложением VLM для проверки. Недоступность зависимости остаётся явной ошибкой.
Для больших групп извлечение тоже идёт окнами с многоуровневым согласованием фактов VLM;
fan-in ограничен `VLM_RECONCILIATION_WINDOWS`, состав группы передаётся интервалами.
Слишком большой/оборванный ответ модели — явная ошибка, без усечения опубликованных реквизитов.
OCR-контекст более 20000 символов на страницу ограничивается с warning; приватный полный
Docling JSON сохраняется до TTL, изображения остаются vision input.
Если суммарный размер исходников окна превышает OCR byte-limit, копирование PDF идёт
в существующем изолированном converter-процессе. Родитель читает окно только после
проверки фактического размера на диске; 400-МиБ источник не превращается в такой же bytes
в API/worker. Слишком тяжёлые окна делятся технически, без изменения границ документов.
Сборка регистрационных PDF-комплектов использует тот же ограниченный дочерний процесс;
worker получает файловые metadata и вычисляет SHA-256 потоком.

`app/domain/taxonomy/letters.json` — единственный каталог: 38 конечных путей, версия 1.0.0.
`taxonomy.py` загружает его в `frozenset`; сервер и extraction prompt используют одну копию.
Промпты скопированы из утверждённого ТЗ и версионируются независимо от JSON 1.0.
Пользователь меняет инструкции своей сессии, но не schema/ownership/page integrity.
При старте снимается копия обоих текстов в задание; последующие правки не влияют на него.
Базовое разделение — `segmentation-v3`, извлечение — `extraction-v3`. Старые snapshots
и сохранённые тексты сессий не перезаписываются; для обновления сохранённых инструкций
восстановите базовый текст каждой из двух вкладок «Промпты» и сохраните.
План хранит короткие VLM-свидетельства страницы: роль, типизированные идентификаторы,
стороны. Они проходят CompactPlan и межоконное согласование. При совпадении
типизированного идентификатора носителя/основной части дальние группы включаются
в запрос независимо от расстояния; их изображения занимают места внутри прежнего
лимита окна. Это подбор контекста, а не объединение: VLM может сохранить отдельные
документы с одинаковым номером дела. Backend отвергает
противоречащие номера конверта/вложения и чужие ссылки, но не перегруппировывает страницы.
Конверт входит в PDF основного документа; полнота main_pages/attachments проверяется отдельно.

Юридический род независим от направления. При organization_hint VLM может распознать
входящий неписьменный акт с пустым template_path. Без контекста направление неизвестно.
Проверка направления сопоставляет полные названия сторон с явно заданной организацией,
нормализуя регистр/кавычки без fuzzy-поиска и скрытого выбора компании из PDF.
VLM извлекает requisites и возвращает все поля one_c=null. После серверной проверки
`application/one_c_projection.py` строит карточку из фактов/доверенного контекста:
внешний отправитель, организация, каталожный маршрут письма, письменный ответ, summary.
Неизвестные реквизиты 1С остаются null. Публичная схема/названия полей JSON 1.0 прежние.
Внутренний `ExtractionDraft.primary_readability` отдельно фиксирует чтение номера/даты:
legible, missing или ambiguous. Низкая уверенность не равна неоднозначности.
Отдельно VLM указывает рукописные собственные поля. Если такое поле отмечено в
low_confidence_fields, ограниченный повтор требует null/ambiguous; простое снятие
пометки не отменяет уже заявленную неопределённость. Ограничение сохраняется и при
дополнительной проверке отправителя, не затрагивая читаемые печатные реквизиты.
Явный статус ambiguous также сохраняется между повторами, даже если VLM пропустила
путь в low_confidence_fields или не указала рукописное начертание.
Противоречащие статусу значения возвращаются модели для ограниченного повтора;
в повтор передаются предыдущий типизированный candidate и конкретные ошибки.
Модель исправляет противоречивое поле, сохраняя независимые читаемые реквизиты;
пересмотр другого факта требует сверки с изображением. Backend значения не копирует.
`facts()` удаляет служебные свидетельства перед проекцией 1С и публичным экспортом.
Для извлечения к полному рендеру добавляется один фрагмент той же страницы,
заново отрисованный из нормализованного PDF с большей детализацией, до 2400 пикселей
по длинной стороне полной страницы. Для первой основной страницы многостраничного
комплекта это верхние 40% с меткой `region=header`, для остальных — нижняя треть.
Расширение верхнего фрагмента сохраняет строку реквизитов, пересекающую границу трети.
Метка header подходит и для старого более узкого рендера. Полное изображение сохраняется;
окно из восьми страниц содержит максимум 16 изображений. Для старого manifest без
детальных рендеров используется нижняя треть обычного превью. Новые пути остаются приватными.
Если у письма пропущен идентификатор отправителя или ссылка на счёт, но OCR содержит метку,
либо неписьменный акт ссылается на судебные дела, выполняется одна дополнительная
VLM-проверка полноты/принадлежности связанных дат. Метка не доказывает значение
или принадлежность отправителю; backend ничего не подставляет из OCR. Штраф без
указания контекста в процессуальном документе возвращается модели для уточнения:
backend не решает, действует взыскание или производство прекращено.

У одновоконного комплекта с физическими приложениями VLM отдельно читает собственную
дату только по изображениям основных страниц: без OCR, дат приложений и кандидата
из предыдущего полного ответа. Приватный `PrimaryDateReading` хранит значение,
читаемость, адрес основной страницы и предупреждения. Backend проверяет согласованность
и принадлежность ссылки; полный ответ затем обязан сохранить именно это решение VLM.
Неоднозначность/отсутствие остаются null, предупреждения чтения сохраняются в результате.
Значения из OCR и эталонов не подставляются. Этот проход относится к извлечению и
использует тот же редактируемый prompt snapshot; публичная схема 1.0 не расширяется.

Задание и outbox создаются в одной транзакции с owner/idempotency/hash и admission limits.
В PostgreSQL admission сериализован advisory lock, переходы задания — row lock.
Worker использует lease, heartbeat и возрастающий fence. Истёкший/отозванный lease не
может обновить snapshot или опубликовать результат. Артефакты каждого fence изолированы.
Recovery ограничивает число восстановлений и общий deadline. Доставка AMQP at-least-once;
повторы outbox разрешены, повторный `claim` активного/terminal задания ничего не запускает.
RabbitMQ содержит только ID, а события, статус и результаты живут в PostgreSQL.
`cursor` и event фиксируются атомарно со снимком.

TTL начинается при success/error/cancel; ожидание без анализа ограничено часом от preview_ready.
Проверка доступа выполняется до чтения и при потоковом скачивании. Reaper не выбирает
активные задания, удаляет файлы, затем DB payload; orphan uploads очищаются после часа.
Sessions и rate-limit records также имеют ограниченный срок жизни. Обычные логи не
содержат OCR, имена документов, prompts, cookies/keys и query tokens.
Значимые операции измеряются общим monotonic timing decorator, Docker logs ротируются.

Анонимная сессия — случайный подписанный HttpOnly/SameSite cookie и запись PostgreSQL.
CSRF привязан к cookie, Origin проверяется точно; интеграции имеют раздельные ключи/owners.
Подписанный URL привязан к owner, REST-пути и expiry. Получатель capability может скачать
только этот артефакт. Ссылка выдаётся на внешний IP, а не Docker DNS или storage path.

Для сквозного комплекта `files[].documents[]` привязывает регистрацию к первому source.
`documents[].pages` содержит только физические страницы этого source. Все исходные адреса,
основная часть и приложения доступны через `/documents/{id}/manifest`, PDF включает весь комплект.
Поля JSON 1.0 не расширяются общей выдуманной нумерацией; предупреждение отмечает сквозной состав.

## Режимы, ревизии и preparation

`ManageBoundaries` использует узкий порт, `BoundaryTransactions` выполняет короткие
row-lock транзакции. Job хранится в существующем JSON: новые поля имеют defaults,
столбец status уже String(32), поэтому DDL-миграция не требуется. Это проверено отдельно
от запуска новых контейнеров; перед обновлением завершите активные старые задания.

`/uploads` создаёт outbox подготовки. Worker claim сохраняет внешний `uploaded`,
но выдаёт fence/lease и независимый preview deadline. Дочерний конвертер передаёт
source/page metadata закрытым stdout pipe; первое превью фиксируется немедленно,
остальные небольшими порциями. Подготовка не вызывает OCR/VLM. В SQL нет изображений.
Физическая последовательность известна ещё до готовности всех PNG. API пагинирует
ready/pending страницы, UI держит не более 24 карточек ленты и 11 миниатюр viewer.

Auto без флагов сохраняет старый headless путь. Review фиксирует immutable proposal
и освобождает lease в `awaiting_confirmation`. Skip использует границы источников;
без ручной правки `/jobs` работает напрямую. Первая ручная правка атомарно включает
skip, меняет source на manual/manual_override и увеличивает revision. VLM proposal
сохраняется для аудита. Полнота означает: все страницы ровно один раз назначены
регистрации или явно исключены. Оригиналы и превью исключённых страниц сохраняются.

Confirm фиксирует глубоко неизменяемый approved snapshot и outbox одной транзакцией.
Повтор утверждённой revision идемпотентен. Правки до lock отзывают старый fence;
после lock сервер возвращает 409. Автоматический VLM-validator и ручная техническая
проверка разделены: ручной план не получает ложный статус verified/confidence.
Extraction может обнаружить приложения внутри фиксированной группы, но не изменить
её страницы. Готовый PDF включает ровно approved страницы; размер проверяется до OCR
ручного режима, SHA-256 вычисляется по фактическому файлу.

Очередь, preparation, processing и ожидание имеют отдельные бюджеты. Restart не
продлевает активный бюджет и не оживляет истёкший lease. Waiting не занимает consumer.
OCR checkpoint привязан к source SHA/page/preset/languages и контрольной сумме JSON;
повреждённый/устаревший cache не используется. Экспортный контракт остаётся 1.0.

Docling получает последовательные запросы одного адаптера с интервалом минимум 1 с.
По умолчанию `DOCLING_ASYNC=true`: один POST /v1/convert/file/async, затем poll
и чтение результата той же task. ID и fingerprint окна атомарно сохраняются в
private storage; restart продолжает ожидание без нового POST. HTTP timeout 180 с
отделён от `DOCLING_TASK_TIMEOUT_SECONDS=600`; polling не чаще раза в 5 с.
ID не попадает в SSE/логи, произвольные пути upstream запрещены. Удаляется только
свой checkpoint после записи всех успешных страниц; shared tasks/results не очищаются.
429/502/503/504 повторяются максимум 5 раз с Retry-After seconds/date или backoff;
пауза свыше 60 с и постоянная перегрузка дают явный отказ. Poll/result повторы не
повторяют конвертацию. Успешные OCR-окна
сохраняются, отмена прерывает ожидание. Shared Docling не перенастраивается.

Лимиты PostgreSQL разделены: команды 120/min, чтение 600/min, preview/thumbnail
2400/min для сети и owner независимо. Они конечны и действуют между процессами.
429 rate_limit имеет Retry-After. UI объединяет SSE-обновления, держит RAM-кеш
до 96 изображений и максимум 4 одновременных запроса; HTTP-дисковое кеширование
приватных файлов остаётся запрещённым. Кеш очищается при смене задания/TTL.
