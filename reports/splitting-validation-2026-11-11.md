# Разделение больших пачек — 11.11.2026

База: локальный main, GitHub и сервер на
`450e95474462f9ff1fb88576bd4faa138493bdab`; shared main
`839d419432fc25bc988e5871f7e53f6d282a2e77`.
Изменения сделаны только в локальном проекте. Commit/push, pull/up.sh и изменение
серверного кода, credentials или shared-конфигурации агент не выполнял.

## Причины и изменения

Сообщение «Слишком много запросов» в web совпадает с собственным `rate_limit`.
Прежние 120/min одновременно ограничивали команды, polling и каждый PNG. SSE
переотрисовывал карточки, а no-store заставлял повторно скачивать те же миниатюры.
Теперь budgets независимы: control 120, read 600, preview 2400/min, отдельно для
сети и owner, с PostgreSQL-счётчиками. UI объединяет обновления, держит до 96
изображений только в RAM, скачивает максимум четыре одновременно. TTL/смена
задания очищают кеш. Чтение при 429 ограниченно повторяется с Retry-After; отмена
прерывает паузу. Автоматические повторы команд не добавлялись.

Разделение VLM больше не требует OCR всей пачки. Изображения готовятся как прежде,
Docling вызывается после фиксации состава для реквизитов. Соседство стыков расширено
для перемешанных листов; backend не назначает семантические границы. Новый базовый
`segmentation-v2` уточняет независимые письма, конверты и несмежные продолжения.
Snapshots и сохранённые тексты сессий не перезаписываются.

После некорректного плана/JSON после ограниченных повторов, неподтверждённого
auto-плана либо отдельного deadline 900 с предлагается `page_fallback`:
по одному физическому листу, статус `awaiting_confirmation`, без извлечения и
финального JSON. Это прямо разрешённый владельцем резервный путь. Требуется
проверка/confirm; backend не объявляет одиночные листы самостоятельными документами.
Ctrl/Cmd позволяет выбрать несмежные страницы и собрать их новой группой.
При разделении такой группы сохраняется порядок остальных регистраций.

Реальный синхронный OCR 501 страницы воспроизвёл HTTP ReadTimeout на тяжёлом окне.
По проверенному OpenAPI Docling Serve 1.38.2 адаптер использует один async POST,
ожидает ту же task и затем читает результат. Task ID/fingerprint сохраняются
атомарно только в private storage; restart продолжает ожидание без повторного POST.
HTTP timeout 180 с отделён от task timeout 600 с, polling — раз в 5 с.
429/502/503/504 имеют конечные повторы с Retry-After; чужие shared task/results
не очищаются. Ошибки и истечение ожидания не маскируются под успешный OCR.

Для нагрузки локально собран PDF из 173-страничного скана: 173 + 173 + 155 листов,
**501 страница, 124 041 888 байт**. Это производный нагрузочный файл, а не
непредоставленный оригинальный 501-страничный файл владельца.

Завершено настоящее OCR-покрытие **501/501**, физические номера и порядок совпадают.
**80 страниц** использованы из действительных OCR checkpoints первоначального
синхронного прогона. Оставшаяся **421 страница** получена через **22 новых async
POST**, **578 poll GET** и **22 result GET**, последовательно. **429: 0**.
Время этого продолжения — **2859,72 с (47 мин 40 с)**; это не свежий замер полного
цикла 501 страницы с нуля. Время первоначальной подготовки/80 готовых OCR-страниц
не включено. Новых VLM-запросов этот OCR-прогон не выполнял.

Получен в том числе результат окна, превышавшего прежний timeout 180 с.
Повторных POST при ожидании одного task ID не было. Произвольный restart между
POST/poll проверен отдельно regression-тестом; сам ресурсный прогон не прерывался.
Частные метрики: `reports/local/split-501-ocr.json`. Результат подтверждает
работоспособность и продолжение OCR, но не обещает дешёвую обработку любого скана:
для проверки границ этот дорогой этап больше не является предусловием.

## Ограничения и обновление

Нельзя обещать точное автоматическое восстановление любой перемешанной пачки.
Неопределённый/ошибочный план предлагается человеку как черновик, не финальный JSON.
Полный VLM-анализ/извлечение всех 501 страниц не является ресурсным OCR-тестом.
Исторические ошибки реквизитов из предыдущего отчёта здесь не объявляются исправленными.
Финальная SSH-проверка: серверный HEAD прежний, git status чистый, API/worker/PostgreSQL
healthy, /health/live отвечает live. Новый deployment остаётся действием владельца.

В приложенном логе `invalid spec: artifacts::` вызван командой `docker compose logs -f`
без каталогов env. Использовать:

```bash
docker compose --env-file .env.example --env-file .env logs -f api worker
```

После обновления восстановить базовый текст вкладки разделения в существующей
сессии, если нужен новый v2. Приватные PDF/JSON не переносятся через Git:
для серверного `--live` нужны обе новые пары и уточнённый суд_ув.json.
Полный `--live` также запускает прежнюю проверку реквизитов; её расхождения нельзя
скрывать успешным тестом границ.
