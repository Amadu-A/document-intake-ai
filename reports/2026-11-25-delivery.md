## Воспроизведение и изменение

До production-правки настоящий отдельный RabbitMQ 4.1 с `consumer_timeout=60000`
и PostgreSQL 16 воспроизвели ошибку: один активный пакет, три ожидающих,
`ready=3`, `unacked=1`, брокер зарегистрировал acknowledgement timeout.
Регрессия ожидаемо завершилась FAIL: `.cache/ack-before.log`, 157,96 с.
Периодический контроль RabbitMQ выполняется примерно раз в минуту;
тест ждёт 130 с, а не заменяет это поведение mock: [RabbitMQ 4.1 consumers](https://www.rabbitmq.com/docs/4.1/consumers#acknowledgement-timeout).

Теперь каждый из фиксированного числа slots получает ровно одно сообщение
с prefetch=1. До ACK получен CancelOk подписки этого slot. После транзакционного
claim в PostgreSQL отправляется ACK, затем работает прежний Analyze с heartbeat
и fencing. Следующего unacked сообщения при ожидании вычислений нет.
После ACK ответственность сохраняет PostgreSQL lease; crash восстанавливается
существующими recovery/outbox. Новой очереди, scheduler, таблицы и миграции нет.
At-least-once, persistent/mandatory/publisher confirms сохранены.

Consumer channel отделён от publisher channel. Закрытый исходный канал не получает
NACK; неопределённый ACK не переотправляется на новом канале. Дочерняя analysis
корутина отменяется и дренируется при невозможности проверить lease.
Task slots ограничены WORKER_CONCURRENCY (default остаётся 1).
Readiness требует реальную подписку в idle либо живой PG lease в busy, при этом
ошибка подключения к брокеру не маскируется существованием lease.

QUEUE_TIMEOUT_SECONDS default/.env.example — 14400. Preview остаётся 3600,
анализ — 14400, lease — 60, attempts — 3; остальные TTL не менялись.
Поздний publish receipt не удаляет новый сигнал; прежнее исправление outbox сохранено.
Waiting после restart не получает новый срок. Старые terminal задания не оживляются.

| Код | Пользовательское сообщение |
| --- | --- |
| queue_timeout | Превышено время ожидания в очереди. Обработка не началась |
| preview_timeout | Превышено время подготовки страниц |
| job_timeout | Превышено время анализа |
| worker_attempts_exhausted | Исчерпан лимит восстановлений worker |

Начальное состояние подготовки теперь `stage=queued`; UI показывает «Ожидает начала
обработки» до claim, без активного шага/фиктивного процента. Последний work_stage
при ошибке сохраняется. Lifecycle события имеют UTC, phase, fence, attempt;
claim/publish/ACK/потеря канала логируются с безопасной hash-корреляцией и без payload.
ACK outcome `sent` означает отправку, а не несуществующий consumer confirm.
Owner-защищённые delivery события имеют fencing-проверку.
