# Проверка корреспонденции и проекции 1С — 12.11.2026

Обновлено 13.11.2026 после согласования владельцем даты в частном эталоне.

Основа: `main` проекта `f2b2fcf39f9287150f2fc28b5e0e3f2898543b92`,
shared infrastructure `839d419432fc25bc988e5871f7e53f6d282a2e77`.
Изучены актуальные инструкции shared и новый ТЗ владельца. На сервере остался исходный
HEAD; API, worker и PostgreSQL healthy. Commit/push и серверное обновление не выполнялись.
В приложенном логе bootstrap/readiness завершились успешно; упала последующая
матрица распознавания `test_real_five_pairs_comparison_matrix`, а не запуск контейнеров.

## Изменения

- Направление и юридический род независимы. Входящий судебный акт сохраняет
  процессуальный род, `is_letter=false`, `template_path=[]`.
- Необязательный `organization_hint` доступен в web до загрузки, обоих multipart API
  и owner-protected snapshot. Без контекста организация/направление не угадываются.
- VLM возвращает пустой `one_c`; программная проекция использует проверенные факты,
  доверенную организацию и закрытый каталог писем. GUID/справочники 1С не ищутся.
- Новые базовые промпты: `segmentation-v3`, `extraction-v2`. Для старой сохранённой
  сессии нужно восстановить базовый текст **обеих** вкладок «Промпты» и сохранить.
- Свидетельства связи конвертов проходят оконное согласование. Совпадение номера
  расширяет контекст независимо от расстояния, но объединение по-прежнему решает VLM.
  Синтетический тест проверяет 38 промежуточных чужих листов и сохранение отдельных
  документов даже при одинаковом номере дела.
- Номер/дата, одновременно заполненные и объявленные неоднозначными, возвращаются
  VLM с диагностикой. Сомнительные рукописные значения сохраняют null при повторе;
  низкая уверенность в читаемом печатном реквизите сама по себе не обнуляет факт.
  Служебный `primary_readability` не попадает в публичный JSON.
- Полное изображение дополняется одним детальным фрагментом из PDF: верхняя треть
  первой основной страницы многостраничного комплекта, иначе нижняя. Детализация
  ограничена 2400 пикселями по длинной стороне полной страницы; восемь страниц —
  максимум 16 изображений. Это проверено на actual vision/JSON endpoint.
- Одна дополнительная VLM-проверка ищет пропущенные идентификаторы/счета либо проверяет
  принадлежность связанных судебных дат. Backend не подставляет значения из OCR.
  Для штрафа в процессуальном документе требуется смысловой контекст суммы:
  действующее взыскание или историческое прекращённое дело определяет VLM.
- Подготовка PNG использует быстрое сжатие без потерь. После обнаруженной задержки
  повторно пройден прежний браузерный тест на 501 страницу с лимитом 30 секунд;
  лимит не увеличивался. Пиксели и физические страницы проверяются отдельно.
- Публичная JSON Schema в точности совпадает с `docs/result-v1.schema.json`, что
  закреплено тестом. Каталог писем, shared-стек, Compose, env/секреты, миграции и TTL
  не изменялись. Изменены только проектные адаптеры рендеров/vision.

## Реальные примеры

Использован локальный новый application/API-код, настоящие shared Docling/VLM через
SSH к `aistation`. AMQP-доставку в этом частном runner заменяет локальный delivery-loop,
состояние — SQLite. PostgreSQL проверяется отдельно. Это не развёртывание нового кода
на сервере и не проверка нового образа через production AMQP consumer.

Эталон судебного скана — четыре комплекта **[1,8], [2,3,4], [5,6], [7]**.
Решение владельца от 12.11 заменяет старые границы из отчёта 11.11.
Для каждого комплекта проверяются реальные скачивание, SHA-256, число страниц и
совпадение пикселей с соответствующими страницами оригинала в исходном порядке.
Номера/даты/суммы, род, направление, реквизиты отправителя и поля 1С сравниваются
предметно. UUID, подписанные URL и confidence не сравниваются буквально.

| Вход / контекст | Результат по согласованному эталону; время исходного прогона |
|---|---|
| Пять прежних примеров | **5/5 файлов, 31/31 фактов, 238/238 проверок структуры/скачивания**, около 352 с |
| Судебный скан, организация задана | `completed_with_warnings`, **113/113** проверок после пересчёта 13.11, около 208 с |
| Судебный скан, организация не задана | `completed_with_warnings`, **117/117** проверок после пересчёта 13.11, около 193 с |

Оба судебных прогона автоматически сформировали правильные четыре комплекта, все
восемь страниц и скачиваемые PDF без потерь. Проверены юридические виды, направление,
проекция 1С, реквизиты отправителя, собственные и связанные даты, письменный ответ,
заседание, адрес отправителя, процент удержания и исторический контекст штрафа.
В пяти прежних примерах претензия с четырьмя приложениями осталась одной регистрацией.
HTTP 429 от Docling/VLM в этих прогонах не было.

**Судебная матрица по согласованному эталону: 230/230.** До согласования было 228/230:
у исполнительного производства на страницах 2–4 эталон задавал
`court_cases[1].date=null`, а модель в обоих контекстах извлекла одинаковую дату.
Проверка исходного OCR подтвердила явную связь этой напечатанной даты с тем же номером
производства; это не дата текущего постановления. 13.11 владелец разрешил использовать
напечатанную дату. В `examples/суд_ув.expected.json` изменено ровно это поле;
исходный `examples/суд_ув.json` сохранён побайтно без изменений.

Сверка 13.11 использует сохранённые реальные ответы предыдущих OCR/VLM-прогонов,
не новый запуск модели. Исходные ответы и прежняя матрица сохранены; критерии теста
не ослаблялись. Восемь проверок PDF/SHA-256/пикселей взяты из фактических скачиваний
этих прогонов; повторного скачивания после TTL не было. Повторный сквозной запуск
через серверный AMQP consumer остаётся частью проверки после развёртывания.

Две дополнительные денежные суммы в ответе сверены с исходным OCR: оба числовых
значения присутствуют в документе. Матрица проверяет наличие утверждённых сумм,
не запрещая извлечение других доступных поисковых реквизитов.

Частные матрицы: `reports/local/classification-five.json` и
`reports/local/classification-final-court.json`. Пересчёт по согласованной дате:
`reports/local/classification-approved-court-2026-11-13.json`; он сохраняет хеши
исходной матрицы и эталона до/после изменения. Ошибки отдельных кейсов сохраняются;
`awaiting_confirmation` сразу фиксируется как `segmentation_requires_review`,
а не ожидается до общего timeout и не подтверждается. Отчёты предыдущих экспериментов
не заменяют результат последнего прогона. Эти выборки не гарантируют точность модели
на произвольных документах.

Частные PDF, полный эталон `examples/суд_ув.expected.json`, диапазоны
`examples/суд_ув_cut.json` и отчёты `reports/local/` остаются вне Git.
На сервере пока есть старый диапазонный `суд_ув.json`; перед `--live` нужно отдельно
передать два новых частных JSON. Оригинальные PDF не изменялись.

## Проверка после обновления

1. Передать частные JSON в серверный `examples/`, выполнить `git pull --ff-only`,
   `bash scripts/up.sh`, затем `bash scripts/test.sh --live`.
2. В web восстановить оба базовых промпта. До выбора файлов указать организацию из
   частного эталона; загрузить судебный PDF и запустить auto.
3. Проверить четыре комплекта: 2, 3, 2 и 1 страница; конверт соединён с повесткой,
   письмо отдельно. Скачать PDF и JSON. Только письмо получает каталожный маршрут 1С.
4. Повторить новым пакетом без организации: direction/one_c.organization должны быть
   null с warning, юридические роды и состав PDF сохраняются. Reload восстанавливает
   контекст текущего задания.

Крупные реальные OCR/разделение описаны в отчёте 11.11; 501-страничный OCR и большой
173-страничный скан в этой итерации повторно не прогонялись через модель.
Наличие offline PASS само по себе не доказывает точность реальной модели.
