# Независимое распознавание регистрационных блоков

## Причина отказа

Диагностика существующего сервера выполнена через `ssh aistation`, без изменения
серверного кода, настроек и контейнеров. Пакет из 173 страниц имел 108 утверждённых
блоков; ранее после 41 результата обработка остановилась на блоке 42, странице 53.
Модель определила процессуальный род, но backend запустил дополнительное чтение
судебных дат `read_related_court_dates`. После `model_output_limit` и повторов
`schema_validation_failed` отказ одного неподдерживаемого документа завершил весь пакет.
Переполнение из-за количества страниц здесь не было причиной: в блоке один лист.

## Поведение после изменения

Каждый готовый блок получает отдельную VLM-классификацию рода/вида/подвида.
Проверенный тип фиксируется в JSON Schema и серверном валидаторе последующего
извлечения. Пока поддерживается только шаблон письма; для неписем возвращаются
тип, краткое описание, PDF и явная заглушка `unsupported_template` без реквизитов.
Проверка судебных дат для таких блоков не вызывается.

Каждый запрос содержит максимум восемь физических страниц. Классификация проходит
все части последовательно, передаёт краткое описание и тип предыдущей части;
block_id, part_index/parts_total, has_previous/has_next явно обозначают продолжение.
Окна извлечения могут перекрываться; проверенные результаты согласует сама VLM
ограниченным деревом. Физические номера и утверждённые границы не меняются.

Ограниченные повторы сохраняются. Их исчерпание для одного блока даёт явный статус
`classification_failed`/`extraction_failed`, PDF и пустые непроверенные поля.
Остальные блоки продолжаются. Общий timeout, отмена, утрата lease и технические
ошибки задания сохраняют прежнее отдельное поведение. Валидность JSON Schema
не доказывает фактическую точность модели; гарантия безошибочной VLM не заявляется.

Готовые результаты блоков сохраняются в PostgreSQL JSON с fingerprint промпта
и страниц, переживают restart worker без повторной VLM. Публичный результат
сохраняет JSON 1.0; диагностика добавлена в snapshot/status, artifacts и короткие
SSE-события. Приватные факты checkpoint, OCR и пути наружу не выдаются.
UI показывает статус каждого блока, число писем/заглушек/неполных результатов,
предупреждение у неполного JSON и доступные ссылки на PDF.

Базовый extraction-v5 обновляет только неизменённую сохранённую базу v4.
Пользовательские тексты и запущенные snapshots сохраняются. Новых секретов и
миграций нет. Проверка deployment smoke дополнительно требует `recognized`
для собственного тестового письма: один доступный PDF не считается успешным анализом.

## Проверки

Реальные вызовы существующего shared-VLM из локального кода:

| Случай | Результат | Максимум страниц в запросе | Время |
| --- | --- | --- | --- |
| Прежний сбойный блок, страница 53 | `unsupported_template`, процессуальный род, без извлечения письма | 1 | 2,62 с |
| Утверждённый блок из девяти страниц | `unsupported_template`, две части 8+1 с продолжением | 8 | 12,17 с |
| `4-2591.pdf`, все шесть страниц | `recognized`, одно письмо, четыре приложения | 6 | 254,64 с |
| Синтетическое письмо, девять страниц | `recognized`; номер и срок ответа только с последнего листа совпали | 8 | 146,30 с |

У претензии совпали все 9 критериев матрицы: классификация, направление, номер/дата,
связанный договор, пеня, срок ответа и диапазоны приложений [3], [4], [5], [6].
Это проверка извлечения уже сформированного блока; приёмка точности автоматических
границ на больших примерах остаётся отдельной задачей.
В девятистраничном письме классификация шла частями 8+1, извлечение — окнами
8 и 3 с перекрытием двух листов, затем согласование без изображений. Использовались реальные
изображения и VLM, без OCR-подсказки и без пользовательских данных.

Повторены все 108 утверждённых диапазонов проблемного пакета из 173 страниц.
Исходный файл найден локально по SHA-256 из диагностики сервера; содержание всех
страниц сверено с сохранённым нормализованным PDF растровым сравнением в масштабе 0,4.
Использованы локальные production worker/REST/SQLite/PDF и реальные запросы shared-VLM
через SSH. OCR взят из проверенного кеша прежнего прогона; разделение и OCR заново
не запускались. Это проверка именно извлечения по утверждённому составу, не нового
развёртывания на сервере и не точности авторазделения.

Итог: `completed_with_warnings`, без общей ошибки, **108 блоков**, **207 VLM-запросов**,
максимум **8 страниц**, время **3745,03 с**. 61 письмо получило `recognized`, 45 документов —
`unsupported_template`. Страница 61 (блок 47) получила `classification_failed` /
`document_type_unresolved`; страница 111 (блок 79) — `extraction_failed` / `vlm_unavailable`.
Эти два результата явно неполны и не считаются распознанными. Все последующие блоки
обработаны. Для всех 108 PDF через REST проверены скачивание, SHA-256, число/порядок
и растровое содержание страниц; все 173 страницы присутствуют ровно один раз.
Эталона фактов всех 61 писем для этой разметки нет, их семантическая точность целиком
не объявляется проверенной.

Штатный `ops/check-quality.ps1 -Browser`: **417 passed, 7 skipped**, покрытие **84%**;
пропущены opt-in live и неприменимые Windows проверки владельца Unix-файла.
После финального уточнения надписи неполного JSON — **23 passed** для браузерной панели,
семантической матрицы и runner; после добавления статусов в runner — **9 passed**;
после усиления smoke — **10 passed** для health/smoke. Chromium проверяет смешанный пакет
«заглушка / отказ извлечения / успешное письмо», reload, предупреждения, экспорт и все PDF.
Снимок `tmp/document-mixed-completed.png` просмотрен; переполнения/перекрытия элементов нет.

Окончательная версия в изолированном Linux-контейнере без сети: Ruff check/format
и полный офлайн-набор — **414 passed, 17 skipped**, покрытие **85%**. Пропущены
opt-in browser/live, два приватных примера вне публичного архива и два Windows-теста.
Настоящая VLM проверялась отдельными описанными выше прогонами; эти skips не названы PASS.
`git diff --check` пройден. Ветка и remote main при проверке — `f4e7d7e`;
новые изменения остались локальными, серверную версию владелец обновляет сам.
Частные материалы находятся только в игнорируемых `reports/local/`, `.cache/` и `tmp/`;
документы, OCR, подписанные URLs и секреты в этот отчёт не включены.

Linux, выполняет владелец:

```bash
cd ~/projects/document-intake-ai
git status --short
git pull --ff-only
bash scripts/test.sh
bash scripts/up.sh
```

`up.sh` пересобирает собственные API/worker и выполняет реальные проверки зависимостей,
HTTP, обработки тестового письма и скачивания. Логи по умолчанию видны.
Прежний terminal job заново не запускается: загрузите пакет повторно.

В `http://192.168.55.3:8084/` после Ctrl+F5 проверить:

1. Подтвердить нужные диапазоны смешанного пакета. Сначала виден этап определения типа,
   затем извлечение. Неписьма помечены «шаблон реквизитов пока не реализован».
2. Письма имеют реквизиты; у неподдерживаемых документов поля пусты, тип и PDF доступны.
   Если отдельный блок не распознан, видна его диагностика, остальные результаты остаются.
3. После завершения JSON экспортируется; пакет с заглушками имеет предупреждения,
   экран явно сообщает о блоках без реквизитов. Скачать PDF каждого диапазона и оригинал,
   сверить состав/порядок страниц. Refresh сохраняет результат и предупреждения.
4. Блок из девяти и более страниц остаётся одной регистрацией и одним PDF;
   обработка частей не создаёт дополнительные диапазоны.
5. Для `4-2591.pdf` при составе [1–6] получить одно письмо и четыре приложения [3], [4],
   [5], [6]. Ошибки автоматических границ проверять отдельно, не скрывать ручной правкой
   в отчёте авторазделения.
